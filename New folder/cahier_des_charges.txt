Plateforme de gestion SCI – Vanille biologique
1. Présentation du projet
Le projet consiste à créer une plateforme numérique de type extranet / application web destinée à gérer un Système de Contrôle Interne (SCI) pour un groupement de producteurs de vanille biologique.
La plateforme doit permettre de centraliser toutes les données liées aux producteurs, parcelles, récoltes, lots, transformations, contrôles internes, non-conformités, stocks, ventes/exportations et documents de certification.
L’objectif principal est de remplacer ou compléter les fichiers papier/Excel par un outil structuré, fiable et exploitable lors des audits de certification biologique.
2. Contexte métier
Le groupement produit de la vanille biologique. Le SCI doit permettre de contrôler les producteurs, garantir la conformité biologique, tracer les lots et préparer les audits externes.
Dans le fonctionnement souhaité, la traçabilité commence dès la récolte de la vanille verte. Cette vanille verte est ensuite collectée, préparée/transformée, stockée puis vendue ou exportée sous forme de vanille préparée.
Le système doit donc suivre le flux complet :
Producteur → Parcelle → Récolte vanille verte → Collecte → Lot vert → Préparation / transformation → Lot préparé → Stock → Vente / export
3. Objectifs de la plateforme
La plateforme doit permettre de :
gérer les producteurs du groupement ;
gérer les parcelles et leur localisation ;
suivre les récoltes de vanille verte ;
suivre les collectes et pesées ;
créer et suivre les lots verts ;
suivre la transformation de la vanille verte en vanille préparée ;
gérer les lots préparés ;
gérer le stock ;
tracer un lot depuis la parcelle jusqu’à la vente/export ;
remonter d’un lot vendu/exporté jusqu’aux producteurs d’origine ;
gérer les inspections internes ;
gérer les non-conformités et actions correctives ;
centraliser les documents nécessaires au SCI ;
générer des rapports utiles pour les audits.
4. Utilisateurs et rôles
La plateforme doit prévoir plusieurs profils utilisateurs avec des droits différents.
4.1 Administrateur
L’administrateur gère l’ensemble de la plateforme.
Droits principaux :
créer/modifier/supprimer des utilisateurs ;
gérer les rôles ;
accéder à toutes les données ;
configurer les paramètres généraux ;
exporter les données.
4.2 Coordinateur SCI
Le coordinateur SCI pilote le système de contrôle interne.
Droits principaux :
gérer les producteurs ;
gérer les parcelles ;
suivre les inspections ;
valider les décisions de conformité ;
gérer les non-conformités ;
consulter les tableaux de bord ;
préparer les rapports d’audit.
4.3 Auditeur interne
L’auditeur interne réalise les inspections des producteurs et des parcelles.
Droits principaux :
consulter les producteurs assignés ;
remplir les fiches d’inspection ;
ajouter photos et observations ;
signaler une non-conformité ;
signer un rapport d’inspection.
4.4 Responsable collecte
Le responsable collecte enregistre les apports de vanille verte.
Droits principaux :
créer une collecte ;
peser/enregistrer les quantités ;
générer un bordereau de collecte ;
associer la collecte au producteur et à la parcelle ;
créer ou alimenter un lot vert.
4.5 Responsable transformation / préparation
Ce rôle suit la transformation de la vanille verte en vanille préparée.
Droits principaux :
sélectionner les lots verts utilisés ;
enregistrer les étapes de préparation ;
saisir les poids d’entrée et de sortie ;
calculer les pertes et le rendement ;
créer un lot préparé.
4.6 Responsable stock
Le responsable stock suit les entrées, sorties et emplacements des lots.
Droits principaux :
enregistrer les entrées en stock ;
enregistrer les sorties ;
affecter un emplacement ;
consulter les quantités disponibles ;
signaler une anomalie de stock.
4.7 Auditeur externe / lecteur
Ce profil dispose d’un accès en lecture seule.
Droits principaux :
consulter les données nécessaires à l’audit ;
consulter les rapports ;
consulter la traçabilité ;
exporter certains documents si autorisé.
5. Workflow métier principal
Le workflow principal doit suivre les étapes suivantes :
Création du producteur.
Création de ses parcelles.
Enregistrement des récoltes de vanille verte.
Collecte et pesée de la vanille verte.
Création d’un lot vert.
Préparation/transformation du ou des lots verts.
Création d’un lot préparé.
Entrée du lot préparé en stock.
Sortie du stock pour vente ou export.
Consultation de la traçabilité complète.
La plateforme doit permettre de suivre ce flux dans les deux sens :
de la parcelle vers la vente/export ;
de la vente/export vers la parcelle d’origine.
6. Modules fonctionnels à développer

Indicateurs souhaités :
nombre total de producteurs ;
nombre total de parcelles ;

nom ;
prénom ;
village ;
téléphone ;
date d’entrée dans le groupement ;
statut : actif, suspendu, exclu ;
statut biologique : conversion, certifié, non certifié ;
surface totale ;
observations ;
documents associés.
6.3 Module Parcelles

Champs principaux :
code parcelle unique ;
producteur lié ;
village/localisation ;
coordonnées GPS ;
superficie ;
culture principale ;
cultures associées ;
historique des intrants ;
risque de contamination ;
statut de conformité ;
photos ;
observations.
6.4 Module Récolte vanille verte
Ce module permet d’enregistrer la vanille verte récoltée avant préparation.
Champs principaux :
code récolte ou code lot vert ;
producteur ;
parcelle ;
date de récolte ;
poids récolté en kg ;
qualité observée ;
maturité ;
observations ;
personne ayant enregistré la récolte.
6.5 Module Collecte
Ce module permet d’enregistrer les apports de vanille verte au point de collecte.
Champs principaux :
numéro de bordereau ;
date de collecte ;
producteur ;
parcelle ou récolte liée ;
poids brut ;
poids net ;
collecteur ;
signature producteur ;
signature collecteur ;
lot vert associé ;
observations.
Le système doit pouvoir générer un bordereau de collecte imprimable ou exportable en PDF.
6.6 Module Lots verts
Un lot vert correspond à une quantité de vanille verte collectée avant préparation.
Champs principaux :
code lot vert unique ;
date de création ;
producteur(s) lié(s) ;
parcelle(s) liée(s) ;
poids total ;
statut : collecté, en préparation, transformé, bloqué ;
destination : transformation / attente / rejet ;
observations.
6.7 Module Transformation / Préparation
Ce module est central. Il permet de suivre la transformation de la vanille verte en vanille préparée.
Le système doit permettre de sélectionner un ou plusieurs lots verts en entrée, puis de créer plusieurs lots préparés en sortie selon les qualités obtenues après préparation et tri.
Après préparation, la vanille doit pouvoir être classée en 4 qualités principales :
Gourmet ;
Standard ;
TK ;
Fendue.
Informations à suivre :
numéro d’opération de transformation ;
date de début ;
date de fin ;
lots verts utilisés ;
poids total en entrée ;
étapes réalisées : échaudage, étuvage/fermentation, séchage, affinage, tri, calibrage, conditionnement ;
responsable de transformation ;
pertes constatées ;
poids final total préparé ;
répartition du poids par qualité : Gourmet, Standard, TK, Fendue ;
rendement global ;
rendement par qualité ;
lots préparés créés ;
observations qualité.
Le système doit calculer automatiquement :
perte en kg ;
taux de perte ;
rendement global ;
rendement par qualité.
Exemple :
Pour 100 kg de vanille verte en entrée, l’opération de transformation peut produire :
12 kg Gourmet ;
5 kg Standard ;
3 kg TK ;
2 kg Fendue.
Dans ce cas, le système doit créer ou permettre de créer quatre lots préparés distincts, chacun avec sa qualité, son poids, son stock et sa traçabilité.
6.8 Module Lots préparés
Un lot préparé correspond à une quantité de vanille prête à être stockée, vendue ou exportée.
Champs principaux :
code lot préparé unique ;
date de création ;
lots verts d’origine ;
poids final ;
catégorie/qualité ;
humidité si disponible ;
statut : en stock, réservé, vendu, exporté, bloqué ;
emplacement stock ;
observations.
6.9 Module Stock
Le module Stock doit suivre les entrées, sorties et emplacements des lots préparés.
Fonctions attendues :
entrée en stock ;
sortie de stock ;
transfert d’emplacement ;

consultation du stock disponible ;
historique des mouvements.
Champs principaux :
lot préparé ;
type de mouvement : entrée, sortie, transfert, correction ;
date ;
quantité ;
emplacement ;
utilisateur responsable ;
justification ;
observation.
6.10 Module Vente / Export
Ce module permet de suivre les sorties commerciales.
Champs principaux :
numéro vente/export ;
date ;
client ;
lot(s) préparé(s) vendu(s) ;
quantité vendue ;
destination ;
documents associés ;
statut : préparé, expédié, clôturé.
6.11 Module Traçabilité
Le module Traçabilité doit permettre deux recherches :
Recherche descendante
À partir d’un producteur ou d’une parcelle, retrouver :
Producteur → Parcelle → Récolte → Lot vert → Transformation → Lot préparé → Stock → Vente/export
Recherche ascendante
À partir d’un lot vendu/exporté, retrouver :
Vente/export → Lot préparé → Transformation → Lots verts → Récoltes → Parcelles → Producteurs
Le système doit afficher clairement :
tous les lots liés ;
les poids à chaque étape ;
les dates ;
les responsables ;
les documents associés ;
les éventuelles non-conformités.

7. Règles de traçabilité
La plateforme doit respecter les règles suivantes :
Aucun lot vert ne peut être créé sans producteur identifié.
Aucun lot vert ne peut être créé sans poids enregistré.
Aucun lot vert ne peut être transformé sans opération de préparation enregistrée.
Aucun lot préparé ne peut être créé sans lien avec un ou plusieurs lots verts.
Aucun lot préparé ne peut être vendu/exporté sans entrée préalable en stock.
Le poids vendu/exporté ne doit pas dépasser le stock disponible.
Les pertes de transformation doivent être enregistrées.
Les rendements doivent être calculés automatiquement.
Un lot non conforme doit pouvoir être bloqué.
Toute modification importante doit être historisée.

11. Résultat attendu
Le résultat attendu est une plateforme numérique permettant de gérer de manière fiable le SCI d’un groupement de producteurs de vanille biologique.
La plateforme doit permettre au groupement de prouver à tout moment :
l’origine de chaque lot ;
la conformité des producteurs ;
la cohérence des volumes ;
les contrôles réalisés ;
les non-conformités traitées ;
les documents disponibles pour audit.
L’objectif final est de disposer d’un outil professionnel facilitant la certification biologique, la traçabilité complète de la vanille et la préparation des audits externes.
12. Workflows métier détaillés
Cette section décrit les principaux parcours métier que la plateforme doit gérer. Chaque workflow doit être respecté par l’application afin d’éviter les erreurs de saisie, les ruptures de traçabilité et les incohérences de stock.
12.1 Workflow Producteur
Objectif : créer et suivre chaque producteur membre du groupement.
Acteur principal : coordinateur SCI ou administrateur.
Étapes : 1. Création de la fiche producteur. 2. Attribution d’un code producteur unique. 3. Saisie des informations personnelles. 4. Saisie du statut biologique. 5. Ajout des documents liés au producteur. 6. Validation de la fiche. 7. Possibilité d’archiver, suspendre ou exclure le producteur.
Données obligatoires :
code producteur ;
nom ;
village ;
téléphone ;
statut du producteur ;
statut biologique ;
date d’entrée dans le groupement.
Contrôles à prévoir :
deux producteurs ne peuvent pas avoir le même code ;
un producteur suspendu ou exclu ne doit pas pouvoir fournir un lot bio ;
une alerte doit apparaître si le contrat producteur est manquant.
Documents générés : fiche producteur PDF, contrat d’engagement si prévu, historique producteur.
12.2 Workflow Parcelle
Objectif : identifier toutes les parcelles liées aux producteurs et suivre leur conformité.
Acteur principal : coordinateur SCI, auditeur interne ou administrateur.
Étapes : 1. Sélection du producteur. 2. Création d’une nouvelle parcelle. 3. Attribution d’un code parcelle unique. 4. Saisie des coordonnées GPS. 5. Saisie de la superficie. 6. Saisie des cultures présentes. 7. Évaluation des risques de contamination. 8. Ajout de photos si nécessaire. 9. Validation de la parcelle.
Données obligatoires :
code parcelle ;
producteur lié ;
superficie ;
localisation ou village ;
statut de conformité.
Données recommandées : coordonnées GPS, photos, historique des intrants, cultures voisines, zone tampon, observations.
Contrôles à prévoir :
une parcelle doit toujours être liée à un producteur ;
une parcelle non conforme ne doit pas permettre la création d’un lot bio ;
si le risque de contamination est élevé, une alerte doit apparaître.
Documents générés : fiche parcelle PDF, carte ou localisation, historique parcellaire.
12.3 Workflow Récolte vanille verte
Objectif : enregistrer la vanille verte récoltée avant toute préparation.
Acteur principal : responsable collecte, coordinateur SCI ou agent terrain.
Étapes : 1. Sélection du producteur. 2. Sélection de la parcelle concernée. 3. Saisie de la date de récolte. 4. Saisie du poids récolté. 5. Contrôle visuel de la qualité et de la maturité. 6. Création d’un enregistrement de récolte. 7. Association de la récolte à une future collecte ou à un lot vert.
Données obligatoires :
producteur ;
parcelle ;
date de récolte ;
poids de vanille verte ;
utilisateur ayant saisi l’information.
Données recommandées : maturité, qualité visuelle, photos, observation sur l’état des gousses, nombre de sacs ou contenants.
Contrôles à prévoir :
impossible d’enregistrer une récolte sur une parcelle non conforme ;
impossible d’enregistrer une récolte pour un producteur suspendu ou exclu ;
alerte si le poids récolté est anormalement élevé par rapport à la parcelle ;
la récolte doit rester traçable jusqu’au lot préparé final.
Documents générés : fiche récolte, historique récolte par producteur, historique récolte par parcelle.
12.4 Workflow Collecte de vanille verte
Objectif : enregistrer les apports de vanille verte au point de collecte et créer les lots verts.
Acteur principal : responsable collecte.
Étapes : 1. Le producteur apporte la vanille verte. 2. Le responsable collecte identifie le producteur. 3. Le responsable collecte sélectionne la récolte ou la parcelle concernée. 4. La vanille est pesée. 5. Le poids brut et/ou net est enregistré. 6. Un bordereau de collecte est créé. 7. Le producteur et le collecteur signent. 8. Un lot vert est créé ou alimenté. 9. Le lot vert passe au statut « collecté ».
Données obligatoires :
numéro de bordereau ;
date de collecte ;
producteur ;
poids collecté ;
responsable collecte ;
lot vert associé.
Données recommandées : parcelle liée, récolte liée, qualité observée, nombre de sacs, photos, signature producteur, signature collecteur.
Contrôles à prévoir :
un producteur non conforme ne peut pas livrer de vanille bio ;
un poids collecté ne peut pas être nul ou négatif ;
la quantité collectée ne doit pas dépasser de manière incohérente la récolte déclarée ;
chaque collecte doit être rattachée à un lot vert ;
chaque bordereau doit avoir un numéro unique.
Documents générés : bordereau de collecte PDF, reçu producteur, registre de collecte journalier, historique des collectes.
12.5 Workflow Lot vert
Objectif : créer et suivre les lots de vanille verte avant préparation.
Acteur principal : responsable collecte ou coordinateur SCI.
Étapes : 1. Création du lot vert à partir d’une ou plusieurs collectes. 2. Attribution d’un code lot vert unique. 3. Association aux producteurs et parcelles d’origine. 4. Saisie du poids total. 5. Statut initial : collecté. 6. Affectation à une transformation future. 7. Suivi du changement de statut : collecté, en préparation, transformé, bloqué.
Données obligatoires :
code lot vert ;
date de création ;
poids total ;
collectes liées ;
producteur(s) d’origine ;
statut.
Contrôles à prévoir :
un lot vert doit toujours avoir au moins une collecte liée ;
le poids du lot vert doit correspondre à la somme des collectes liées ;
un lot vert bloqué ne peut pas être transformé ;
un lot vert déjà transformé ne peut pas être réutilisé sans justification.
Documents générés : fiche lot vert, historique du lot, rapport de composition du lot.
12.6 Workflow Transformation / Préparation
Objectif : tracer la transformation de la vanille verte en vanille préparée, puis classer la vanille préparée par qualité.
Acteur principal : responsable transformation / préparation.
Étapes : 1. Création d’une opération de transformation. 2. Sélection d’un ou plusieurs lots verts en entrée. 3. Enregistrement du poids total entrant. 4. Saisie des étapes de préparation réalisées. 5. Suivi des pertes de poids. 6. Saisie du poids final préparé total. 7. Tri et classification de la vanille préparée en quatre qualités : Gourmet, Standard, TK, Fendue. 8. Saisie du poids obtenu pour chaque qualité. 9. Calcul automatique du rendement global. 10. Calcul automatique du rendement par qualité. 11. Création d’un ou plusieurs lots préparés, séparés par qualité. 12. Clôture de l’opération.
Étapes de préparation à tracer :
échaudage ;
étuvage / fermentation ;
séchage ;
affinage ;
tri ;
calibrage ;
conditionnement.
Qualités de sortie à gérer :
Gourmet ;
Standard ;
TK ;
Fendue.
Données obligatoires :
numéro d’opération ;
date de début ;
lot(s) vert(s) utilisés ;
poids total entrant ;
poids final préparé total ;
poids par qualité ;
responsable ;
lot(s) préparé(s) créé(s).
Calculs automatiques :
perte en kg = poids entrant - poids final préparé total ;
taux de perte = perte / poids entrant ;
rendement global = poids final préparé total / poids entrant ;
rendement Gourmet = poids Gourmet / poids entrant ;
rendement Standard = poids Standard / poids entrant ;
rendement TK = poids TK / poids entrant ;
rendement Fendue = poids Fendue / poids entrant.
Contrôles à prévoir :
impossible de créer une transformation sans lot vert ;
impossible d’utiliser un lot vert bloqué ;
le poids final total ne peut pas être supérieur au poids entrant sauf justification exceptionnelle ;
la somme des poids par qualité doit correspondre au poids final préparé total ;
un rendement anormal doit déclencher une alerte ;
chaque lot préparé doit être lié à l’opération de transformation ;
chaque lot préparé doit avoir une qualité obligatoire.
Documents générés : fiche de transformation, rapport de rendement global, rapport de rendement par qualité, historique des lots verts utilisés, fiches lots préparés.
12.7 Workflow Lot préparé
Objectif : créer et suivre les lots de vanille préparée prêts à être stockés, vendus ou exportés.
Acteur principal : responsable transformation, responsable stock ou coordinateur SCI.
Étapes : 1. Création automatique ou manuelle du lot préparé après transformation. 2. Attribution d’un code lot préparé unique. 3. Association aux lots verts d’origine. 4. Saisie du poids final. 5. Saisie de la qualité ou catégorie. 6. Entrée en stock. 7. Suivi du statut : en stock, réservé, vendu, exporté, bloqué.
Données obligatoires :
code lot préparé ;
date de création ;
opération de transformation liée ;
lots verts d’origine ;
poids final ;
statut.
Contrôles à prévoir :
un lot préparé doit toujours avoir un lot vert d’origine ;
un lot préparé bloqué ne peut pas être vendu ;
le poids du lot préparé doit correspondre à la sortie de transformation ;
tout changement de statut doit être historisé.
Documents générés : fiche lot préparé, rapport de traçabilité, étiquette lot si nécessaire.
12.8 Workflow Stock
Objectif : suivre les entrées, sorties et emplacements des lots préparés.
Acteur principal : responsable stock.
Étapes : 1. Entrée du lot préparé en stock. 2. Attribution d’un emplacement. 3. Suivi des mouvements. 4. Sortie partielle ou totale pour vente/export. 5. Correction éventuelle avec justification. 6. Inventaire périodique.
Données obligatoires :
lot préparé ;
type de mouvement ;
date ;
quantité ;
emplacement ;
responsable.
Contrôles à prévoir :
le stock ne peut jamais devenir négatif ;
une sortie ne peut pas dépasser la quantité disponible ;
un lot bloqué ne peut pas sortir pour vente/export ;
toute correction de stock doit être justifiée ;
l’historique des mouvements doit être conservé.
Documents générés : fiche de stock, registre des mouvements, inventaire, rapport de stock disponible.
12.9 Workflow Vente / Export
Objectif : enregistrer la sortie commerciale des lots préparés.
Acteur principal : coordinateur SCI, responsable stock ou administrateur.
Étapes : 1. Création d’une vente ou export. 2. Sélection du client ou destinataire. 3. Sélection des lots préparés concernés. 4. Saisie des quantités vendues/exportées. 5. Vérification du stock disponible. 6. Association des documents commerciaux ou de certification. 7. Sortie de stock. 8. Clôture de la vente/export.
Données obligatoires :
numéro de vente/export ;
date ;
client ou destination ;
lot(s) préparé(s) ;
quantité ;
statut.
Contrôles à prévoir :
un lot vendu doit être disponible en stock ;
un lot bloqué ne peut pas être vendu ;
la quantité vendue ne peut pas dépasser le stock ;
après validation, le stock doit être mis à jour automatiquement ;
la vente/export doit conserver la traçabilité complète des lots.
Documents générés : fiche vente/export, rapport de traçabilité du lot vendu, documents associés, rapport de sortie de stock.
12.10 Workflow Inspection interne
Objectif : permettre au SCI de contrôler les producteurs, les parcelles et les pratiques biologiques.
Acteur principal : auditeur interne.
Étapes : 1. Planification de l’inspection. 2. Sélection du producteur à inspecter. 3. Sélection de la ou des parcelles. 4. Remplissage de la checklist. 5. Ajout d’observations et photos. 6. Détection éventuelle de non-conformités. 7. Signature du producteur et de l’auditeur. 8. Génération du rapport. 9. Validation par le coordinateur SCI.
Données obligatoires :
producteur ;
auditeur ;
date ;
résultat ;
checklist ;
signature ou validation.
Contrôles à prévoir :
un auditeur ne doit pas inspecter sa propre exploitation ;
une inspection doit avoir un résultat clair ;
une non-conformité détectée doit pouvoir créer automatiquement une fiche non-conformité ;
un producteur non inspecté doit apparaître comme inspection manquante.
Documents générés : rapport d’inspection PDF, historique des inspections, synthèse annuelle des inspections.
12.11 Workflow Non-conformité
Objectif : gérer les écarts détectés dans le SCI.
Acteur principal : coordinateur SCI ou auditeur interne.
Étapes : 1. Création de la non-conformité. 2. Classification : mineure ou majeure. 3. Association au producteur, parcelle ou lot concerné. 4. Définition de l’action corrective. 5. Attribution d’un responsable. 6. Définition d’une date limite. 7. Suivi de la résolution. 8. Clôture après vérification.
Données obligatoires :
numéro de non-conformité ;
date ;
type ;
description ;
niveau de gravité ;
responsable ;
statut.
Contrôles à prévoir :
une non-conformité majeure doit pouvoir bloquer un producteur, une parcelle ou un lot ;
une non-conformité ouverte doit apparaître dans le tableau de bord ;
une action corrective en retard doit générer une alerte ;
la clôture doit être validée par une personne autorisée.
Documents générés : fiche non-conformité, registre des non-conformités, historique des actions correctives.
12.12 Workflow Traçabilité
Objectif : permettre de retrouver l’historique complet d’un produit dans les deux sens.
Recherche descendante : Producteur → Parcelle → Récoltes → Collectes → Lots verts → Transformations → Lots préparés → Stock → Vente/export
Recherche ascendante : Vente/export → Lot préparé → Transformation → Lots verts → Collectes → Récoltes → Parcelles → Producteurs
Informations à afficher :
codes des lots ;
poids à chaque étape ;
dates ;
responsables ;
statuts ;
documents associés ;
non-conformités éventuelles ;
rendements de transformation.
Contrôles à prévoir :
aucune rupture de lien ne doit exister entre lot préparé et lots verts ;
les poids doivent rester cohérents ;
toute incohérence doit être signalée ;
un rapport complet doit pouvoir être exporté.
Documents générés : rapport de traçabilité complet, rapport de composition d’un lot préparé, rapport mass balance.

14. Principes techniques de traçabilité
Le développeur devra garantir les principes suivants :
Chaque lot préparé doit pouvoir remonter jusqu’aux producteurs d’origine.
Chaque transformation doit conserver l’historique exact des lots verts utilisés.
Chaque vente/export doit conserver la liste exacte des lots préparés vendus.
Aucun lien de traçabilité ne doit pouvoir être supprimé sans historique.
Les calculs de rendement et de pertes doivent être automatiques.
Les incohérences de poids doivent déclencher des alertes.
Les suppressions de données sensibles doivent être limitées ou historisées.
Toutes les opérations importantes doivent conserver :
date ;
utilisateur ;
modification effectuée.

18. Règles métier automatiques, contrôles et alertes
Cette section décrit les règles que le système doit appliquer automatiquement pour sécuriser le SCI, éviter les erreurs de saisie, maintenir la traçabilité et signaler les incohérences.
18.1 Règles générales de sécurité des données
Le système doit conserver un historique des actions importantes.
Actions à historiser :
création d’un producteur ;
modification d’un producteur ;
suspension ou exclusion d’un producteur ;
création ou modification d’une parcelle ;
création d’une récolte ;
création d’une collecte ;
création ou modification d’un lot vert ;
transformation d’un lot vert ;
création d’un lot préparé ;
mouvement de stock ;
vente/export ;
création ou clôture d’une non-conformité ;
génération d’un document important.
Pour chaque action, le système doit conserver :
date ;
heure ;
utilisateur ;
action réalisée ;
ancienne valeur si modification importante ;
nouvelle valeur.
18.2 Règles sur les producteurs
Règles obligatoires :
Chaque producteur doit avoir un code unique.
Deux producteurs ne peuvent pas avoir le même code.
Un producteur suspendu ne peut pas livrer de vanille bio.
Un producteur exclu ne peut pas livrer de vanille bio.
Un producteur non certifié ne doit pas pouvoir alimenter un lot bio sans validation spécifique.
Le système doit signaler les producteurs sans contrat signé.
Le système doit signaler les producteurs sans parcelle enregistrée.
Alertes souhaitées :
contrat manquant ;
statut biologique manquant ;
producteur sans inspection annuelle ;
producteur avec non-conformité ouverte ;
producteur suspendu tentant d’être utilisé dans une collecte.
18.3 Règles sur les parcelles
Règles obligatoires :
Une parcelle doit toujours être liée à un producteur.
Chaque parcelle doit avoir un code unique.
Une parcelle non conforme ne peut pas générer une récolte bio.
Une parcelle suspendue ou bloquée ne peut pas être utilisée pour créer un lot bio.
Une parcelle doit conserver son historique de conformité.
Alertes souhaitées :
coordonnées GPS manquantes ;
surface manquante ;
historique des intrants manquant ;
risque de contamination élevé ;
parcelle sans inspection ;
parcelle proche d’une zone à risque si les données GPS le permettent.
18.4 Règles sur les récoltes de vanille verte
Règles obligatoires :
Une récolte doit toujours être liée à un producteur.
Une récolte doit toujours être liée à une parcelle.
Le poids récolté doit être supérieur à zéro.
Une récolte ne peut pas être créée pour un producteur suspendu ou exclu.
Une récolte ne peut pas être créée sur une parcelle non conforme.
Une récolte utilisée dans une collecte doit conserver son lien avec la collecte.
Alertes souhaitées :
poids anormalement élevé par rapport à la surface ;
récolte sans collecte associée après un délai défini ;
récolte saisie sans information qualité ;
récolte issue d’une parcelle à risque.
18.5 Règles sur la collecte
Règles obligatoires :
Chaque collecte doit avoir un numéro de bordereau unique.
Chaque collecte doit être liée à un producteur.
Le poids net doit être supérieur à zéro.
Le producteur doit être actif.
Le producteur doit être conforme pour la filière bio.
La collecte doit être liée à un lot vert ou pouvoir créer un lot vert.
Une collecte validée ne doit pas pouvoir être supprimée sans autorisation spéciale.
Alertes souhaitées :
poids collecté supérieur au poids récolté déclaré ;
collecte sans signature ;
collecte sans parcelle ou récolte liée ;
collecte non encore affectée à un lot vert ;
collecteur non identifié.
18.6 Règles sur les lots verts
Règles obligatoires :
Un lot vert doit avoir un code unique.
Un lot vert doit contenir au moins une collecte.
Le poids total du lot vert doit correspondre à la somme des collectes associées.
Un lot vert bloqué ne peut pas être transformé.
Un lot vert transformé ne peut pas être modifié sans justification.
Un lot vert ne peut pas être utilisé deux fois dans deux transformations différentes sauf si une gestion partielle des quantités est prévue.
Le système doit conserver l’historique des collectes composant le lot.
Alertes souhaitées :
écart entre poids du lot et somme des collectes ;
lot vert sans destination ;
lot vert en attente de transformation depuis trop longtemps ;
lot vert contenant une collecte issue d’un producteur avec non-conformité ouverte ;
lot vert bloqué.
18.7 Règles sur la transformation / préparation
Règles obligatoires :
Une transformation doit toujours utiliser au moins un lot vert.
Un lot vert bloqué ne peut pas être transformé.
Le poids entrant doit être égal à la somme des poids des lots verts utilisés ou des quantités partielles utilisées.
Le poids final préparé total ne peut pas être supérieur au poids entrant sauf justification exceptionnelle.
La somme des poids par qualité doit être égale au poids final préparé total.
Les qualités autorisées sont : Gourmet, Standard, TK, Fendue.
Chaque qualité produite doit générer un lot préparé distinct ou une ligne de sortie distincte.
La transformation doit calculer automatiquement les pertes et rendements.
Une transformation clôturée ne doit pas pouvoir être modifiée sans autorisation spéciale.
Alertes souhaitées :
rendement global anormal ;
rendement par qualité anormal ;
poids final supérieur au poids entrant ;
répartition qualité incomplète ;
transformation commencée mais non clôturée ;
lot vert déjà utilisé ;
absence de responsable transformation.
18.8 Règles sur les lots préparés
Règles obligatoires :
Un lot préparé doit avoir un code unique.
Un lot préparé doit toujours être lié à une transformation.
Un lot préparé doit toujours être lié à un ou plusieurs lots verts d’origine.
Un lot préparé doit obligatoirement avoir une qualité : Gourmet, Standard, TK ou Fendue.
Un lot préparé doit avoir un poids supérieur à zéro.
Un lot préparé bloqué ne peut pas être vendu ou exporté.
Un lot préparé doit entrer en stock avant toute vente/export.
Tout changement de statut doit être historisé.
Alertes souhaitées :
lot préparé sans emplacement stock ;
humidité manquante si cette donnée est obligatoire dans le fonctionnement réel ;
lot préparé non entré en stock ;
lot préparé bloqué ;
incohérence entre poids du lot préparé et sortie de transformation.
18.9 Règles sur le stock
Règles obligatoires :
Le stock disponible ne peut jamais être négatif.
Une sortie de stock ne peut pas dépasser la quantité disponible.
Un lot bloqué ne peut pas sortir du stock pour vente/export.
Toute correction de stock doit être justifiée.
Chaque mouvement de stock doit être historisé.
Chaque mouvement doit avoir une date, une quantité, un utilisateur et un type de mouvement.
Types de mouvements minimum :
entrée ;
sortie ;
transfert ;
correction ;
blocage ;
déblocage.
Alertes souhaitées :
stock faible ;
sortie supérieure au stock disponible ;
lot sans emplacement ;
correction de stock importante ;
écart entre stock théorique et inventaire physique.
18.10 Règles sur les ventes / exports
Règles obligatoires :
Une vente/export doit avoir un numéro unique.
Une vente/export doit être liée à un ou plusieurs lots préparés.
Les lots vendus doivent être disponibles en stock.
Les lots vendus ne doivent pas être bloqués.
La quantité vendue ne peut pas dépasser la quantité disponible.
Une vente/export validée doit automatiquement créer une sortie de stock.
La traçabilité des lots vendus doit rester consultable après la vente/export.
Alertes souhaitées :
document export manquant ;
certificat manquant ;
lot bloqué sélectionné ;
quantité supérieure au stock ;
vente/export non clôturé ;
destination manquante.
18.11 Règles sur les inspections internes
Règles obligatoires :
Chaque producteur doit avoir au moins une inspection annuelle.
Chaque inspection doit avoir un auditeur identifié.
Chaque inspection doit avoir un résultat clair.
Un auditeur ne doit pas inspecter sa propre exploitation.
Une inspection avec non-conformité doit pouvoir générer automatiquement une fiche de non-conformité.
Les rapports d’inspection doivent être archivés.
Alertes souhaitées :
producteur non inspecté ;
inspection incomplète ;
inspection sans signature ;
inspection sans résultat ;
non-conformité détectée mais non enregistrée.
18.12 Règles sur les non-conformités
Règles obligatoires :
Chaque non-conformité doit avoir un numéro unique.
Chaque non-conformité doit avoir un niveau de gravité.
Une non-conformité majeure doit pouvoir bloquer un producteur, une parcelle ou un lot.
Chaque non-conformité doit avoir un statut.
Une non-conformité clôturée doit conserver son historique.
Une action corrective doit avoir un responsable et une date limite si nécessaire.
Statuts minimum :
ouverte ;
en cours ;
clôturée ;
rejetée ;
en retard.
Alertes souhaitées :
action corrective en retard ;
non-conformité majeure ouverte ;
non-conformité sans responsable ;
non-conformité sans décision ;
lot concerné toujours en circulation malgré blocage.
18.13 Règles sur la traçabilité
Règles obligatoires :
Le système doit permettre une traçabilité descendante.
Le système doit permettre une traçabilité ascendante.
Aucun lot préparé ne doit exister sans origine.
Aucun lot vendu/exporté ne doit exister sans lot préparé.
Les poids doivent être visibles à chaque étape.
Les pertes de transformation doivent être calculées.
Les documents associés doivent être accessibles depuis la vue traçabilité.
Les non-conformités liées doivent être visibles.
Alertes souhaitées :
rupture de lien de traçabilité ;
lot préparé sans lot vert ;
vente/export sans lot préparé ;
poids incohérents entre étapes ;
documents manquants.
18.14 Règles sur les documents
Règles obligatoires :
Les documents générés doivent être archivés.
Chaque document doit être lié à un objet métier si applicable.
Chaque document doit conserver sa date de génération.
Chaque document doit conserver l’utilisateur qui l’a généré.
Un document important remplacé doit conserver l’ancienne version si possible.
Alertes souhaitées :
contrat producteur manquant ;
rapport inspection manquant ;
bordereau collecte manquant ;
fiche transformation manquante ;
document export manquant ;
certificat manquant.

18.16 Niveaux d’alerte
Le système peut classer les alertes selon trois niveaux :
Information
Exemples :

récolte sans photo ;
lot en attente.
Attention
Exemples :

rendement inhabituel ;
GPS manquant ;
action corrective bientôt en retard.
Critique
Exemples :
lot bloqué sélectionné pour vente ;
producteur exclu utilisé dans une collecte ;
rupture de traçabilité ;
stock négatif ;
non-conformité majeure ouverte.
18.17 Principe général de validation
Le système doit empêcher les actions critiques lorsque les conditions minimales ne sont pas respectées.
Exemples :
empêcher la vente d’un lot bloqué ;
empêcher la transformation d’un lot vert bloqué ;
empêcher la création d’un lot préparé sans origine ;
empêcher une sortie de stock supérieure au stock disponible.
Pour les cas moins critiques, le système peut afficher une alerte mais laisser continuer avec justification.
Exemples :
rendement inhabituel ;
document manquant ;
GPS manquant ;
poids final exceptionnel.
Dans ce cas, l’utilisateur doit saisir une justification, qui sera historisée.
19. Gestion des rôles, permissions et sécurité utilisateur
Cette section décrit les rôles utilisateurs de la plateforme et les permissions associées.
Le système doit être basé sur une gestion des accès sécurisée.
Chaque utilisateur doit uniquement accéder aux modules et actions autorisés selon son rôle.
19.1 Principes généraux de sécurité
Le système doit respecter les principes suivants :
Chaque utilisateur doit avoir un compte individuel.
Les mots de passe doivent être sécurisés.
Les accès doivent dépendre du rôle utilisateur.
Les actions importantes doivent être historisées.
Les utilisateurs inactifs peuvent être désactivés.
Les suppressions critiques doivent être limitées.
Les connexions et modifications importantes doivent être traçables.
Le système doit enregistrer :
date de connexion ;
utilisateur ;
adresse IP si possible ;
actions importantes réalisées.

être réservées aux administrateurs ;
être historisées ;

19.17 Principe général de sécurité

20. Exigences techniques et architecture recommandée
Cette section décrit les attentes techniques de la plateforme. Elle doit servir de base de discussion avec le développeur ou l’agence informatique.
L’objectif est de créer un outil fiable, sécurisé, évolutif et utilisable sur le terrain.
20.1 Type de solution attendue
La solution souhaitée est une application web de type extranet.
Elle doit être accessible depuis :
ordinateur ;
tablette ;
smartphone ;
navigateur web moderne.
La solution doit être responsive, c’est-à-dire adaptée automatiquement aux différentes tailles d’écran.
20.2 Application web ou mobile
Pour la première version, il est recommandé de développer une application web responsive.
Avantages :
accès simple depuis navigateur ;
pas besoin d’installation sur téléphone ;
maintenance plus simple ;
mise à jour centralisée ;
coût de développement plus maîtrisé.
Une application mobile native pourra être envisagée plus tard si nécessaire.
20.3 Progressive Web App – option recommandée
Il serait pertinent de prévoir une application web progressive appelée PWA.
Une PWA permet :
une utilisation proche d’une application mobile ;
un raccourci sur l’écran d’accueil du téléphone ;
une meilleure expérience mobile ;
une possible gestion du mode hors ligne dans une version avancée.
Cette option est fortement recommandée pour les utilisateurs terrain.
20.4 Mode hors ligne
Le mode hors ligne est un besoin important mais peut être développé en version avancée.
Objectif : permettre aux agents terrain de saisir certaines données même sans connexion internet.
Données concernées en priorité :
inspections internes ;
photos terrain ;
coordonnées GPS ;
récoltes ;
collectes.
Fonctionnement attendu :
L’utilisateur saisit les informations hors ligne.
Les données sont stockées temporairement sur l’appareil.
Dès que la connexion revient, les données sont synchronisées.
Le système signale les erreurs éventuelles de synchronisation.
Priorité :
V1 : fonctionnement en ligne ;
V2 ou V3 : mode hors ligne et synchronisation.
20.5 Architecture recommandée
Architecture possible :
Frontend : React, Next.js ou équivalent ;
Backend : API sécurisée ;
Base de données : PostgreSQL ;
Authentification : système sécurisé avec rôles ;
Stockage fichiers : stockage cloud sécurisé ;
Hébergement : serveur cloud ou plateforme managée.
Une solution basée sur Supabase peut être envisagée pour :
base de données PostgreSQL ;
authentification ;
stockage fichiers ;
sécurité par rôles ;
API automatique.
Le choix final devra être validé par le développeur selon le budget, les compétences et les besoins de maintenance.

23. MVP, périmètre de développement et priorités projet

comprendre les priorités ;

L’objectif est d’éviter un projet trop complexe dès la première version.
23.1 Objectif principal de la V1
La première version de la plateforme doit avant tout permettre :
une traçabilité complète de la vanille ;
la gestion des producteurs et parcelles ;
la gestion des récoltes et collectes ;
la gestion des lots verts ;
la gestion de la transformation ;
la gestion des qualités de vanille préparée ;
le suivi du stock ;
le suivi des ventes/exports ;
la préparation des audits SCI.
La priorité absolue est la cohérence des données et la continuité de la traçabilité.

23.5 Priorités métier du projet
Le développeur devra comprendre que les priorités du projet sont :
Priorité 1
Traçabilité complète de la vanille.
Le système doit pouvoir retrouver l’origine complète d’un lot préparé ou vendu.
Priorité 2
Cohérence des poids et rendements.
Le système doit empêcher les incohérences importantes.
Priorité 3
Simplicité terrain.
Les utilisateurs doivent pouvoir utiliser la plateforme facilement même avec un faible niveau informatique.
Priorité 4
Préparation des audits SCI et Ecocert.
Le système doit permettre de produire rapidement les preuves et rapports nécessaires.
Priorité 5
Évolutivité.
Le système doit pouvoir évoluer sans devoir être entièrement reconstruit.
23.6 Contraintes du projet
Le prestataire devra tenir compte des contraintes suivantes.
Utilisation terrain
La plateforme sera utilisée sur le terrain.
Elle doit donc être :
simple ;
rapide ;
lisible sur mobile ;
robuste.
Connexion internet variable
Le système doit fonctionner correctement même avec une connexion moyenne.
Le mode hors ligne pourra être développé plus tard.
Utilisateurs non techniques
L’interface doit rester simple.
Le projet ne doit pas dépendre d’utilisateurs très techniques.
Traçabilité obligatoire
La traçabilité ne doit jamais être cassée.
Toutes les relations doivent être conservées.
23.7 Critères de réussite de la V1
La V1 sera considérée comme réussie si les conditions suivantes sont remplies.
Traçabilité
un lot préparé peut être tracé jusqu’au producteur ;
une vente/export peut être tracée jusqu’aux parcelles d’origine ;
aucune rupture de traçabilité.
Transformation
les rendements sont calculés ;
les qualités sont séparées ;
les pertes sont calculées.
Stock
le stock est cohérent ;
les mouvements sont historisés ;
les sorties sont contrôlées.
SCI
les producteurs et parcelles sont gérés ;
les données auditables sont disponibles ;
les documents SCI peuvent être générés.
Utilisation
les utilisateurs terrain peuvent utiliser la plateforme ;
les workflows sont simples ;
les principales opérations sont rapides.
23.8 Éléments pouvant être simplifiés pour accélérer la V1
Pour limiter les coûts et accélérer le développement, certains éléments peuvent être simplifiés dans un premier temps.
Exemples :
GPS simple sans carte avancée ;
documents PDF simples ;
tableau de bord basique ;
pas de mode hors ligne ;
pas de QR code ;
pas de notifications SMS ;
pas d’application mobile native.
Ces éléments pourront être améliorés plus tard.
23.9 Recommandation de stratégie projet
Il est fortement recommandé :
de développer une V1 stable ;
de tester sur le terrain ;
d’ajuster les workflows réels ;
ensuite seulement développer les fonctionnalités avancées.
Cette approche permettra :
de limiter les coûts ;
d’éviter les erreurs ;
d’obtenir rapidement un outil exploitable ;
de faire évoluer le système progressivement.
